# Brainstorming Tree

简体中文 | [English](README.md)

**一个用于持久化人机脑暴的轻量级 Agent Plugin。** 它把想法保存为可审计的 Idea Tree（创意树），让长时间的探索能够抵抗上下文遗忘、内容干扰和会话中断。

> **项目状态：** 早期开发阶段（`v0.3.0`）。与具体 Agent 无关的持久化核心已经实现；跨 Agent 打包和面向设计目标的真实脑暴验证仍待完成。哪些结论可在本仓库内独立复现，见下方[当前进度](#当前进度)。

## 为什么要做这个项目

Brainstorming Tree 只有一个目的：一个人和一个 AI 一起讨论，产出有价值的研究想法。这个目的背后有两个持续存在的难点——保持足够轻量以便真正被使用，以及抵抗"自动研究退化为参数搜索"的拉力，也就是换个参数的同一个机制冒充成新想法。

一次长时间脑暴会要求语言模型同时记住很多东西：最初目标、不同分支、被否定的假设、已有证据、修改过程，以及一个方案为什么取代另一个方案。随着对话增长，早期信息可能离开当前上下文，也可能被后续无关内容稀释。常见结果是：重复提出旧想法、忘记约束、前后判断不一致，或丢失原本值得继续探索的分支。

Brainstorming Tree 把这部分状态移出对话记忆。对话仍然是交互界面，但项目本地的创意树会成为唯一可信状态来源。

## 核心方案

Agent Plugin 由四个刻意保持简单的部分组成：

1. **可移植的 Agent Skill：** 规定人机循环——谁提出想法、AI 什么时候必须停下来、人说的话如何变成被记录的判断。
2. **本地 MCP 服务器：** 提供类型明确的创意树操作，避免依赖模型反复改写长篇文字来维持一致性。
3. **SQLite 数据库：** 在当前工作区保存树、节点、比较和事件。
4. **轻量运行时适配层：** 对接不同 Agent Host 各自的清单、配置和安装约定。

当 Host 没有加载 MCP 服务器时，**CLI 包装** `scripts/idea_tree_cli.py` 用同一套工具驱动同一个服务端：

```bash
python3 scripts/idea_tree_cli.py <tool> '<json args>' [workspace]
```

```text
用户目标
   │
   ▼
Agent + 可移植脑暴技能
   │  类型明确的操作（MCP 工具，或 CLI 包装）
   ▼
本地创意树服务端
   │  数据库事务
   ▼
<workspace>/.idea-tree/ideas.sqlite3
```

运行时以本地为主，只依赖 Python 标准库。核心循环不需要云端服务、账号、向量模型或第二个 LLM。

## 跨 Agent 兼容边界

可移植核心建立在两个开放接口上：

- [Model Context Protocol（MCP）](https://modelcontextprotocol.io/specification/2025-11-25)：承载类型明确的工具和 Host–Server 通信。
- [Agent Skills](https://agentskills.io/specification)：承载 `SKILL.md` 行为约定。

“Agent Plugin”代表这个项目的产品边界：状态引擎、MCP 工具和脑暴行为不属于某一个 Agent 产品。但这**不代表**所有 Agent 都能用同一个安装包零配置运行。每个 Host 必须支持对应的开放接口，并且可能需要一个很薄的适配层来处理自己的清单、启动命令、权限或安装路径。

当前仓库保留 `.codex-plugin/plugin.json`，把它作为第一个 Codex 适配层。它只是兼容入口，不是项目身份或架构边界。后续 Agent 适配层应保持轻量，并复用同一个服务端和 Agent Skill。

## 循环

人提问。AI 读人给的材料，提出机制上真正不同的叶子。人给反馈。循环继续，反馈里的每一次判断都落到树上，成为一次比较或一次删除。

三个动作驱动这棵树：

| 动作 | 加了什么 | 触发条件 |
| --- | --- | --- |
| **横向（WIDE）** | 第一层叶子，依赖一条现有活叶子都不依赖的假设——来自否定共享假设、借邻近领域的机制，或人的提示。 | 开局，直到至少有三个机制上真正不同的方向；人把所有方向都否掉时再来一轮。 |
| **纵向（DEEP）** | 某个叶子的子节点，多出一条具体承诺。 | 该叶子赢过比较，或被人点名。输掉的叶子从不加深。 |
| **合成（MERGE）** | 两个幸存叶子的综合方案，前提是假设不冲突。 | 两个活叶子互补而不是互相矛盾。 |

一条规则把整个循环撑住：**AI 绝不在同一回合里既加节点又记比较。** 新叶子必须先摆给人看，比较来自人接下来说的话。

## 账本强制的规则

- **两条防参数搜索的闸门。** 归一化假设集与某个活跃兄弟相同的节点会被拒收。相对父节点没有增加任何假设的子节点会作为参数变体被拒收——它只能记成父节点上的一次比较。
- **排名来自已记录的比较。** 对成对比较做 Bradley-Terry 聚合，既按兄弟组给出，也给出整棵树的候选短名单。每一条都带 `agent_only` 和用户比较次数，所以"人从没插手过的排名"是看得见的。
- **墓碑。** 删除记录理由，并保留节点。
- **版本检查。** 每次修改和删除都要传 `expected_version`，陈旧的模型上下文无法覆盖更新后的状态。
- **取代链。** 树的目标被冻结。前提变了就用 `supersedes` 开一棵新树；旧树拒绝写入，并指出它的后继。

快照还会返回 `shared_assumptions`——所有活跃想法共享的假设——好让下一轮横向去挑战这块从未被质疑的地基，而不是在它上面继续微调。

## v0.2 尝试过什么，以及为什么被移除

`v0.2` 是一个强推断判断账本：`select` 操作按"能分开多少尚未被支配的分支 / 成本"给待定甄别项打分；一份由 `user` / `inferred` / `assumed` 标记的问题与约束构成的目标契约；带成本和 Platt 过滤的观察；每次比较背后都要有类型明确的评估；以及用 Pareto 支配做剪枝。第一次真实实战证明这些机制判断得很好，却什么都没生成：树建完之后再没长过，所有比较都是 agent_only，人一次判断也没做——这个循环只有收敛机制，没有发散机制，也没有给人留下动作的位置。发散和人的回合现在放进了 Skill 的循环里，服务端只负责存储和排序。

## 目标能力

- **状态持久化：** 即使上下文被压缩或进程中断，也可以继续之前的讨论。
- **关系明确：** 每个想法都保留父节点、前任方案和综合来源。
- **修改可审计：** 每次变更都会留下事件记录。
- **避免陈旧覆盖：** 通过版本检查，阻止旧上下文覆盖更新后的状态。
- **删除可追溯：** 删除只创建墓碑标记，不物理抹掉历史。
- **数据本地化：** 默认由当前项目工作区持有脑暴数据。

## 计划中的使用流程

1. 向兼容的 Agent 提供一个问题、决策或开放式想法。
2. 建立一棵目标被冻结的创意树。
3. 让 Agent 提出机制上真正不同的叶子、摆出来给你看，并把你的反馈记成比较和删除。
4. 在之后的会话中继续使用同一棵树，而不需要从聊天记录重新拼接状态。
5. 输出最强的存活叶子，同时说明它背后的比较、仍然打开的分支，以及什么会让这个决定重新开启。

## 设计原则

- 状态必须存在于模型之外。
- 证据高于表达能力和模型信心。
- 想法只针对具名对手、在具名判据上排序，从不孤立打分。
- 反例和失败分支是学习资产，必须保留。
- 可靠的最小机制优先于功能数量。
- 服务端负责存储和排序；Skill 负责发散和与人对话。

## 数据与隐私

数据库位于 `<workspace>/.idea-tree/ideas.sqlite3`，默认会被 Git 忽略。它可能包含敏感脑暴内容；分享、导出或修改忽略规则前，请先检查其中的数据。本地 `docs/` 目录也会被忽略，避免工作记录被意外发布。

`v0.3` 使用 schema 版本 3，不提供从 `v0.1` 或 `v0.2` 的迁移路径。打开旧版数据库会报错并指明该工作区；请删除该数据库或改用另一个工作区，不要继续复用它。
