# Brainstorming Tree

简体中文 | [English](README.md)

**一个用于持久化、强推断式脑暴的轻量级 Agent Plugin。** 它把想法保存为可审计的 Idea Tree（创意树），让长时间运行的 Agent 工作能够抵抗上下文遗忘、内容干扰和会话中断。

> **项目状态：** 早期开发阶段（`v0.2.0`）。与具体 Agent 无关的持久化核心已经实现；跨 Agent 打包、自动化测试套件和长期真实脑暴项目验证仍待完成。哪些结论可在本仓库内独立复现，见下方[当前进度](#当前进度)。

## 为什么要做这个项目

Brainstorming Tree 只有一个目的：一个人和一个 AI 一起讨论，产出有价值的研究想法。这个目的背后有两个持续存在的难点——保持足够轻量以便真正被使用，以及抵抗"自动研究退化为参数搜索"的拉力，也就是换个参数的同一个机制冒充成新想法。

一次长时间脑暴会要求语言模型同时记住很多东西：最初目标、不同分支、被否定的假设、已有证据、修改过程，以及一个方案为什么取代另一个方案。随着对话增长，早期信息可能离开当前上下文，也可能被后续无关内容稀释。常见结果是：重复提出旧想法、忘记约束、前后判断不一致，或丢失原本值得继续探索的分支。

Brainstorming Tree 把这部分状态移出对话记忆。对话仍然是交互界面，但项目本地的创意树会成为唯一可信状态来源。

## 核心方案

Agent Plugin 由四个刻意保持简单的部分组成：

1. **可移植的 Agent Skill：** 规定如何选择、扩展、评估和综合想法。
2. **本地 MCP 服务器：** 提供类型明确的创意树操作，避免依赖模型反复改写长篇文字来维持一致性。
3. **SQLite 数据库：** 在当前工作区保存节点、上下级关系、评估、版本和操作历史。
4. **轻量运行时适配层：** 对接不同 Agent Host 各自的清单、配置和安装约定。

```text
用户目标
   │
   ▼
Agent + 可移植脑暴技能
   │  类型明确的操作
   ▼
本地 MCP 服务器
   │  数据库事务
   ▼
<workspace>/.idea-tree/ideas.sqlite3
```

运行时以本地为主，只依赖 Python 标准库。核心循环不需要云端服务、账号、向量模型或第二个 LLM。

## 跨 Agent 兼容边界

可移植核心建立在两个开放接口上：

- [Model Context Protocol（MCP）](https://modelcontextprotocol.io/specification/2025-11-25)：承载类型明确的工具和 Host–Server 通信。
- [Agent Skills](https://agentskills.io/specification)：承载 `SKILL.md` 行为约定。

“Agent Plugin”代表这个项目的产品边界：状态引擎、MCP 工具和脑暴行为不属于某一个 Agent 产品。但这**不代表**所有 Agent 都能用同一个安装包零配置运行。每个 Host 必须支持对应的开放接口，并且可能需要一个很薄的适配层来处理自己的清单、启动命令、权限或安装路径。

当前仓库保留 `.codex-plugin/plugin.json`，把它作为第一个 Codex 适配层。它只是兼容入口，不是项目身份或架构边界。后续 Agent 适配层应保持轻量，并复用同一个 MCP 服务器和 Agent Skill。

## 强推断式脑暴

Brainstorming Tree 用强推断学科的方式给想法排序：从不孤立打分，总是针对一个具名对手、在一个具名判据上比较，只在证据支持时才剪枝。

| 阶段 | 实际行为 |
| --- | --- |
| **扩展（Expand）** | 添加机制上真正不同的方向、可验证想法或综合方案，每个都带有明确的假设和 kill condition。 |
| **比较（Compare）** | 在一个具名判据上记录两个兄弟节点之间的成对比较，并附带证据：实验、来源、逻辑链或用户的明确判断。 |
| **甄别（Discriminate）** | 给每个待定的甄别项——一条观察，或一个被标记为 inferred/assumed 的问题或约束——按"能分开多少尚未被支配的分支 / 其成本"打分，对分数最高的一项采取行动；没有任何一项达标时，回落为比较被检验最少的节点。 |
| **剪枝（Prune）** | 只有当某个其他活跃候选在迄今全部比较中都胜出且无平局时，才判该分支出局；未被比较过的分支从不视为更差。 |

这个项目早期版本直接搬用了蒙特卡洛树搜索（MCTS）的控制循环：用置信上界分数选择、用标量评估、把标量回传给全部祖先节点。这一套后来被移除：成对的 LLM 判断明显比让模型给单个想法孤立打分更可靠；树搜索只有在负责区分候选的判别器足够准（LLM 判据通常达不到这个准度）时才优于对候选做一次简单的重新排序；而执行之前给出的标量分数系统性地偏高。树留下来的只是血缘与证据的账本，不是搜索程序；排序来自对已记录比较结果的 Bradley-Terry 聚合，而不是走一遍分数。

有两条规则专门防住"自动研究"最常见的退化方式：悄悄换个参数重跑同一个想法。子想法或综合方案必须比它的非根父节点多出至少一个假设，否则会被拒绝——一个参数变体不能冒充新机制，只能作为父节点上的一次比较或评估记录下来。当所有存活想法都共享某个从未被质疑的假设时，读取操作会把它作为 `shared_assumptions` 返回，提示下一步该去挑战这块共同地基，而不是在它上面继续做微调。

## 目标能力

- **状态持久化：** 即使上下文被压缩或进程中断，也可以继续之前的讨论。
- **关系明确：** 每个想法都保留父节点、前任方案和综合来源。
- **修改可审计：** 每次变更和评估都会留下操作记录。
- **避免陈旧覆盖：** 通过版本检查，阻止旧上下文覆盖更新后的状态。
- **删除可追溯：** 删除只创建墓碑标记，不物理抹掉历史。
- **数据本地化：** 默认由当前项目工作区持有脑暴数据。

## 计划中的使用流程

1. 向兼容的 Agent 提供一个问题、决策或开放式想法。
2. 建立一棵具有不可变目标、成功条件和停止条件的创意树。
3. 由插件选择分支、加入不同候选方案，并记录有证据支持的评估。
4. 在之后的会话中继续使用同一棵树，而不需要从聊天记录重新拼接状态。
5. 输出最强的存活综合方案，同时说明决定性证据、未解决分支和重新开启条件。

## 设计原则

- 状态必须存在于模型之外。
- 证据高于表达能力和模型信心。
- 想法只针对具名对手、在具名判据上排序，从不孤立打分。
- 反例和失败分支是学习资产，必须保留。
- 可靠的最小机制优先于功能数量。

## 数据与隐私

计划中的数据库位于 `<workspace>/.idea-tree/ideas.sqlite3`，默认会被 Git 忽略。它可能包含敏感脑暴内容；分享、导出或修改忽略规则前，请先检查其中的数据。本地 `docs/` 目录也会被忽略，避免工作记录被意外发布。

`v0.2` 使用全新 schema（`SCHEMA_VERSION = 2`），不提供从 `v0.1` 的迁移路径。打开 `v0.1` 数据库会报错并指明该工作区；请删除该数据库或改用另一个工作区，不要继续复用它。
